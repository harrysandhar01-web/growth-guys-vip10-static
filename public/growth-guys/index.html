01

Start with the event, not a promise

The current Growth Guys checkout-code question is documented through VIP10: the dedicated record identifies the observed code response, cart context, date, and evidence boundary. This hub organizes the surrounding questions—item availability, cart totals, shipping, gateway presentation, and later checkout conditions—without turning one observation into a universal promise.

Start with the current VIP10 record for the dated code result, then use these guides to read the merchant’s live cart and published terms carefully. The merchant controls inventory, eligibility, prices, tax, shipping, gateways, and future checkout conditions.

02

Browse by checkout question

Use the cart guide for the cart-only boundary; the code compatibility checklist for item and session variables; the order-total explanation for subtotal, discount, shipping, tax, and gateway distinctions; and the public-cart-log guide for the evidence fields a record should include.

If the storefront changes, becomes unavailable, or presents a different payment gateway, the correct response is to log the condition—not to force an old result to look current.

03

Merchant-reported current-batch endotoxin-report status

Growth Guys reports that its current batches include endotoxin reports alongside its established Janoshik multi-vial COA process. Earlier inventory from the transition period may show the original COA without an endotoxin result. Availability, batch linkage, method, and result should be checked in the document for the individual product and batch.

Growth Guys’ public laboratory-results library is the closest merchant source for current product and batch reports. A report for purity or mass is not automatically an endotoxin report, so readers should use the individual report’s stated method and sample or batch identifier.

04

Keep each checkout field distinct

A storefront observation can contain several facts at once, but they should not be collapsed into one conclusion. Product availability answers whether a candidate was selectable at that moment. A coupon response answers what the cart displayed for a particular code. A listed shipping line answers what was shown for the visible destination context. A payment gateway answers what method was exposed—not whether payment would ultimately succeed.

This hub is organized around those distinctions so that a changing field can be updated without rewriting unrelated evidence. If a gateway disappears, that affects gateway context. If a product sells out, that affects test availability. If a code is rejected, that affects the documented cart response. Treating each as a separate field produces a record that can be audited rather than a slogan that becomes misleading when one storefront condition changes.

05

What this desk does not collect

The desk does not collect customer accounts, payment credentials, personal contact information, order-confirmation data, or purchase outcomes in order to create a verification entry. Those data are unnecessary for the limited question the archive is designed to answer and would blur the line between an ordinary public cart check and an attempted transaction.

Data minimization strengthens the record. It keeps the event focused on visible product, cart, discount, gateway, shipping, tax, timing, and screenshot context. It also means readers should not interpret the archive as a review of merchant fulfilment, delivery, customer service, payment success, or individual eligibility—none of those facts are established by the method.
